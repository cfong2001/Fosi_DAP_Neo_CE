## Surprises and leads

- Module 1 data names a manufacturing-style media path: UTF-16LE strings 'Media Init...', 'LowFormat...', 'SysAreaCopy...' sit alongside the slot-validator code. Stage names for low-level media initialisation/format operations exist in the resident update path. No separate 'engineering mode' module was found among the 82 records.
- Module 12 carries a second, CD-ROM inquiry identity: the last 28 bytes of its code region are the ASCII string 'RockChip    CD-ROM      1.00', next to the Fosi disk identity stored twice in its data. That is the shape of Rockchip's virtual CD-ROM personality (driver/update disc); whether the Neo ever enumerates it is a device-side question this image cannot settle.
- Module 33 data embeds the ASF header GUID (75B22630-668E-11CF-A6D9-00AA0062CE6C) and a pointer table into the 0x308c694 stub window. The system-side codec dispatcher knows the WMA container and dispatches into the small stub family (modules 41/42/50–57), whose purpose is still open.
- Modules 54, 56 and 57 are byte-identical code (700 bytes each); 53 and 55 differ by one byte each. Five near-duplicate template overlays with 2–22-byte data records. Purpose unknown.
- Zero-tail overlays: module 39 is 97.9% zeros past byte 0xbf0 and module 61 is 92% zeros past 0x1aa4; their table lengths reserve max-size overlay windows rather than describing dense code.
- Module 0 data holds the complete ID3v1 genre table (~147 names, 'Blues' to 'Psybient'), MBR error strings ('Invalid partition table', 'Error loading operating system', 'Missing operating system') and an interleaved test-like marker 'TTEESSTTMP3'.
- Video-container traces in audio decoders: modules 73 and 77 (AAC/ALAC) parse MP4 box tables that include video entries ('avcC', 'vide', 'vidiosamplesum = %d' in 73). The strings prove the demuxer code exists; they do not prove the DAP Neo plays video.
- Recording-folder strings are SDK residue until proven otherwise: 'U:\RECORD     \VOICE' (modules 22, 38), 'U:\RECORD     \FM' (module 23) and 'RECORD' (module 61) are folder-name strings in shared-SDK-style overlays. No microphone/FM-tuner driver evidence was found in this catalog, matching the caution in repo/analysis/DP3_V137.md.
- No hidden/diagnostic command strings (no AT-command set, no 'engineering mode', no test-menu text) were found in any module's distinctive strings. Module 12's single 'SBC' byte hit is inside instruction bytes, not a string, and is not Bluetooth evidence.
- 19 of 82 records carry no payload at all (2, 13–16, 28, 40, 43–49, 58–60, 62, 70); module 40 is BSS-only (8 KB reservation) and module 70 is an empty placeholder in the second-core window.

## Method and limits

- Strings: ASCII runs ≥4 chars from code+data, filtered by a documented distinctiveness score (format/path/keyword bonuses, Thumb-immediate noise penalties); UTF-16LE runs from data regions only. Full lists with file offsets are in module_catalog.json (up to 40 per module).
- Vector tables: strict shape test (aligned SP, odd reset, ≥7 identical odd default-handler words). Only modules 0 and 71–80 pass; the other code modules begin with function prologues (e.g. PUSH 0xE92D/0xB5xx), i.e. they are called overlays, not reset images.
- Entropy is Shannon entropy over the raw region bytes; the 'nonzero span' exposes zero-padded overlay windows.
- This catalog does not disassemble control flow; identifications marked 'likely' and all 'unknown' modules are the open set for Ghidra work. No device was accessed.
