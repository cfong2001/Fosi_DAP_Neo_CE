# DP3_V137.img binary analysis

## Provenance and limits

The input is the supplied stock update package `DP3_V137.img`, 13,631,492 bytes (`0xD00004`), SHA-256 `fcc1cd3e35b46f1f8dbcb8da39fcc5eb3f1d469cdfade5e9c6ea3bd71ac6deef`.

This is an RKnano *firmware update package*, not a raw physical flash dump. Its table assigns separate load and execution addresses to code, initialized data and BSS. It cannot establish the installed bootloader, partition table, secure-boot fuses, persistence layout or peripheral wiring. ARM execution addresses below are virtual/core-visible values from the package; the physical flash mapping is still unknown.

## Header, integrity, sections

| File offset | Value / interpretation |
| --- | --- |
| `0x000` | Packed BCD date `2026-10-22` (`26 20 22 10`) |
| `0x010` | `Rockchip` |
| `0x030` | `RKnano SDK 1.0` |
| `0x1f4` | Little-endian `0x00c94000` pointer to duplicate 512-byte header |
| `0x1f8` | `RKnanoFW` magic |
| `0x200` | `0x03050000` module load base |
| `0x204` | `82` module records |
| `0x208` | First record; each record occupies 32 bytes |
| `0xc94000` | Exact byte-for-byte duplicate of file `[0:0x200]` |
| `0xd00000` | Four-byte CRC trailer begins |

The stored trailer is little-endian `0x5cda4157`. For every byte before the trailer, shift the accumulator left eight bits and index the MSB-first CRC table with `(crc >> 24) ^ byte`. Polynomial `0x04c10db7`, initial CRC zero, no reflection and no final XOR reproduce `0x5cda4157`. This is a reproducible package-integrity check, not evidence of a signature. Cryptographic verification by another component is not ruled out.

An entry in the module directory contains eight little-endian `uint32_t` values in this order:

```
code_load, code_exec, code_len,
data_load, data_exec, data_len,
bss_exec, bss_len
```

For nonempty initialized regions, `file_offset = load_addr - 0x03050000 + 0x200`. `*_exec` gives a CPU execution address, *not* the file offset. Several modules occupy overlapping execution windows; loading every module at once is incorrect. `bss_len` describes memory to clear, not payload bytes. Some records have no executable region and must not be treated as code.

## Processor images and memory

Module 0 stores 171,028 original code bytes beginning at file `0x296ac`, executing from `0x03050000`. The first two words of the code vector table are `0x03004000` (initial SP) and `0x03061f8b` (Thumb reset address); the actual instruction address is `0x03061f8a`. Module 0 initialized data load offset is file `0x572c0`, with execution destination `0x03004000`, and BSS starts at `0x030059ac`. The vector format and Thumb-2 instructions support ARM M-profile firmware; the exact processor/SOC revision cannot be established from the image alone.

Module 71 begins another execution image at `0x01000000`, with initial SP `0x01022000` and reset vector `0x0000298d` (likely an alias or core-local mapping). Modules 71 through 80 reuse that execution window with alternate images. Do not equate the `0x01000000` execution address with a confirmed physical flash address. The second executable family is consistent with a second processor/core image, but neither CPU topology nor boot order has been reproduced on hardware.

## Reconstructed updater path

Module 8 contains the updater code at execution address `0x0307e53c` (original code starts at file `0x84264`, length `0x418`). These are machine instruction observations, not decompiler guesses:

1. `0x0307e64c` enters a routine that constructs a firmware filename from a template and opens the file through `0x03058cc6`. The stock data contains 8.3 name templates `DP3_V100IMG` and `RKNANOFWIMG`; both names are *templates/embedded constants*, not proof of the exact search order on every device.
2. `0x0307e6fa` passes an allocated 512-byte buffer to `0x03058fa8` to read a firmware header. At `0x0307e710`, a call to `0x03054ebe` compares eight bytes at header offset `0x1f8` with `RKnanoFW`.
3. `0x0307e718` loads the word at header offset `0x1f4`, adds `0x104000`, then executes `BFC r6,#0,#20`, clearing the low 20 bits. The result is `0x00d00000` for this package. The instruction sequence is relevant to the updater's rounded length, but is not a general validation of any arbitrary image.
4. `0x0307e730` reads the header mirror into a second buffer. At `0x0307e73e` the same `0x03054ebe` comparator checks all `0x200` bytes against the first buffer. Failed comparisons branch to cleanup.
5. `0x0307e75c` calls `0x0307e53c` with 16 sectors to begin copying. More 16-sector chunks are processed from `0x0307e78c` onward. At `0x0307e7e4` the remaining image is handled by the helper at `0x0307e880`. A failed operation branches to the common error path.
6. The helper `0x0307e53c` makes a device operation call through `0x03067912` followed by an operation through `0x030678ca` into a temporary buffer and a `memcmp` of `count << 9` bytes. Its chunk size is capped at 16 sectors, with 512 bytes per sector. This is a **write, read-back, compare** pattern rather than a plain copy loop.

The generic device interface is visible in module 0. `0x030678ca` looks up a device record via `0x030678b0`, loads the callback pointer from `[record + 4]` and calls it with `BLX`. `0x03067912` loads `[record + 8]` instead. The updater passes device selector `0x00030000` to both wrappers. Because it reads into a scratch buffer via the +4 callback and sends source bytes via the +8 callback, +4 is consistent with *read* and +8 with *write* for this device. The underlying controller implementation and physical sector mapping still need to be followed; this is **not** a verified safe flashing procedure.

The routine at `0x030594a0` implements four seek modes through a file-state record, including seek absolute (`r1=0`) and relative (`r1=1`). `0x03058fa8` reads a file via the same file-state record. The high-level roles are supported by actual callers and control flow, not merely suggestive names.

No embedded package signature or decrypted container was required to recover the code/resources in this file. That does not disprove external verification by the ROM or a distinct bootloader.

## USB and user interface

The binary contains a SCSI inquiry identification string at file `0x82282`: `Fosi    Audio DSP Neo   1.00`. Near it, USB mass-storage interface descriptors include class/subclass/protocol bytes `08 06 50` (mass-storage, SCSI transparent, bulk-only transport). This demonstrates a USB MSC implementation in the update binary. Module 11 separately implements USB Audio Class 1.0: 48 kHz, stereo 16-bit PCM on isochronous OUT endpoint 0x02, plus HID consumer-control endpoints. Its original code sets up USB endpoints, moves PCM into a 0x9000-byte ring buffer and accesses hardware register base 0x60080800. The concrete descriptor graph, USB IDs and instructions are documented in `analysis/usb_audio.md`; module 12's MSC descriptor selection is in `analysis/usb_msc.md`.

The resource block at `0x8ad470` begins `ROCK26IMAGERES  `, followed by 456 image records. Each 16-byte record has four little-endian `uint16_t` coordinates/dimensions (`width,height,x,y`) and two little-endian `uint32_t` values (`byte_length,offset_from_resource_start`). All 456 pixel payloads satisfy `byte_length = width * height * 2`, consistent with RGB565. The largest demonstrated full-screen image is 240 by 320 pixels. Its presence does not establish display controller or bus interface.

The multilingual block begins with 21 language table offsets. Each language contains 266 fixed-width records of 258 bytes. Per record, the leading two bytes encode the sequential string ID and the UTF-16LE text begins at record offset +58. English is language index 2. Its labels include `USB Audio` (ID 136), `USB DAC Mode` (143), `Bluetooth` (10), `EQ Settings` (173), `Low Gain` (182), `High Gain` (183), and `Format TF Card` (241). They are useful UI leads, not a hardware register map. Shared SDK labels for FM radio, recording and games are insufficient to establish that the DAP Neo supports those peripherals or exposes those menus.

## Original instruction execution

Module 39 at execution address `0x0307d5fc` contains an ASCII uppercasing routine. The next routine at `0x0307d608` uppercases both arguments and returns the subtraction in `r0`. A strict Thumb-2 subset interpreter reads original opcode halfwords from the matching stock image and executes `SUB.W`, `CMP`, `IT LS`, `SUB`, `SUBS`, and `BX LR` as encountered. Unknown opcodes abort. Its self-check executed 128 uppercase calls plus 128 x 128 comparisons (16,512 executions total) and all returned expected results. This demonstrates actual original code execution for these leaf functions only. It does not emulate the CPU exception model, RTOS scheduler, memory-mapped hardware or main playback engine.

## Reproduction

```sh
python3 tools/rknano_image.py DP3_V137.img info
python3 tools/rknano_image.py DP3_V137.img unpack extracted/
python3 tools/rknano_image.py DP3_V137.img elf 0 module0.elf
python3 tools/rknano_image.py DP3_V137.img elf 8 module8.elf
llvm-objdump -d --mcpu=cortex-m3 module8.elf
python3 tools/rknano_image.py DP3_V137.img lang 2
python3 tools/rknano_image.py DP3_V137.img images
python3 tools/trace_casefold.py DP3_V137.img --verify
python3 tools/trace_casefold.py DP3_V137.img --compare 0x61 0x42 --trace
```

The parser and tracer are read-only. No firmware writes or device modifications are needed.

## Remaining questions

The high-value unfinished work is identifying the physical storage controller beneath verified device-3 callbacks (`0x0305fb64` and `0x0305dd32`; see `analysis/block_device_dispatch.md`), the exact boot/update handoff, the second executable family's boot mapping, the USB Audio/MSC personality switch, the path from the USB PCM ring buffer into the DAC or I2S block, scheduler entry points, and GPIO/I2C/SPI ownership. A physical board inspection or separate bootloader dump may be necessary to settle hardware-specific conclusions. Until then, do not claim specific codec wiring, security bypasses, hidden engineering modes, or a safe modified firmware image.
